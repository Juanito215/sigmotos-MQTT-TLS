. Conceptos: ¿Qué es Object Storage?

Antes de crear nada, necesitas entender qué es lo que estás usando.
Sistema de archivos vs Object Storage

Cuando guardas un archivo en tu computadora, lo haces en un sistema de archivos (como NTFS en Windows o ext4 en Linux). Este sistema organiza los datos en carpetas y subcarpetas, formando una jerarquía.

Object Storage (almacenamiento de objetos) es diferente:

Característica
	

Sistema de archivos
	

Object Storage (S3)

Organización
	

Carpetas jerárquicas
	

Plano (todo al mismo nivel)

Identificación
	

Ruta del archivo
	

Clave única (key)

Acceso
	

Local / red local
	

HTTP desde cualquier lugar del mundo

Escala
	

Terabytes (limitado)
	

Exabytes (ilimitado)

Modificación
	

Se puede editar en sitio
	

Reemplazar el objeto completo

Precio
	

Costo del disco
	

Pago por lo que usas

En S3 no existen carpetas reales. Cuando ves esp32/v1.0.0/firmware.bin, en realidad ese es el nombre completo del objeto (llamado key). La / es solo parte del nombre — S3 la interpreta visualmente como carpeta, pero internamente no hay jerarquía.
Anatomía de AWS S3

Bucket: Es el contenedor raíz. Su nombre debe ser único globalmente en todo AWS (como un dominio de internet). Tú eres el dueño del bucket.

Objeto: Cada archivo almacenado. Tiene:

    key — el nombre/ruta completo
    body — el contenido del archivo (el binario del firmware)
    metadata — información adicional (fecha, tamaño, etiquetas)

Versionado en S3

Cuando habilitas el versionado en un bucket, S3 guarda automáticamente cada versión de un objeto cuando lo sobreescribes.

esp32/v1.0.0/firmware.bin  →  versión A (subida el lunes)
esp32/v1.0.0/firmware.bin  →  versión B (sobreescrita el martes)

Con versionado activado, ambas versiones existen. Puedes recuperar la versión A aunque hayas subido la B. Sin versionado, la versión A se pierde para siempre.
Conceptos de IAM (Gestión de Identidad)

IAM (Identity and Access Management) es el sistema de permisos de AWS. Define quién puede hacer qué con qué recursos.

Componentes que usaremos:

    Usuario IAM — una identidad programática (para scripts y CI/CD, no para humanos)
    Política — un documento JSON que describe permisos (Allow o Deny sobre acciones)
    Access Key — par de claves (ID + secreto) que identifica al usuario IAM en el CLI y APIs

El principio de mínimo privilegio dice: da solo los permisos estrictamente necesarios. Nuestro usuario de GitHub Actions solo necesitará escribir en un bucket específico — nada más.


3. El bucket como subdominio propio

Esta sección explica uno de los aspectos más importantes y menos documentados de S3: el nombre del bucket no es arbitrario si quieres acceder a él con tu propio dominio.
Cómo construye AWS las URLs de un bucket

Cuando creas un bucket, AWS te da automáticamente una URL con este formato:

https://{nombre-del-bucket}.s3.{region}.amazonaws.com/{key}

Ejemplo con un bucket llamado firmwares.denkitronik.com:

https://firmwares.denkitronik.com.s3.sa-east-1.amazonaws.com/esp32/v1.0.0/firmware.bin

Esa URL funciona, pero es larga y no te pertenece. Si mañana migras de AWS, todos tus dispositivos dejan de poder descargar firmwares porque la URL cambia.

La solución profesional: usar tu propio dominio.
La regla de oro: el nombre del bucket debe ser el subdominio

Si quieres que tus firmwares sean accesibles en:

https://firmwares.tuempresa.com/esp32/v1.0.0/firmware.bin

Entonces el bucket debe llamarse exactamente firmwares.tuempresa.com.

AWS usa el nombre del bucket como parte del enrutamiento HTTP. Cuando un navegador o dispositivo hace una petición a firmwares.tuempresa.com, el servidor DNS la redirige al servidor de AWS, y AWS usa el nombre del host para saber a qué bucket servir el contenido.

Reglas para el nombre del bucket

El nombre de tu bucket debe ser:

    Entre 3 y 63 caracteres
    Solo letras minúsculas, números y guiones - y puntos .
    No puede empezar ni terminar con guión

	7. Estructura del bucket: nombres reales

El proyecto iot-mqtt-tls usa una convención de nombres plana y directa:

s3://firmwares.denkitronik.com/
├── firmware_v1.0.0.bin      ← binario de la versión 1.0.0
├── firmware_v1.1.0.bin      ← binario de la versión 1.1.0
├── firmware_v1.2.0.bin      ← binario de la versión 1.2.0
└── firmware_dev-2026-04-16_10-30.bin  ← build de desarrollo (rama main)

El nombre del archivo incluye la versión directamente: firmware_{version}.bin.

Esta simplicidad tiene una ventaja: el mensaje MQTT que el dispositivo recibe incluye la URL completa del binario. El ESP32 no necesita "adivinar" la ruta — la recibe junto con la orden de actualización.
Versionado semántico

Usa SemVer (Semantic Versioning) con el formato exacto vMAJOR.MINOR.PATCH:

v1.0.0  →  v1.0.1  (corrección de bug en conexión MQTT)
v1.0.1  →  v1.1.0  (nueva función: portal de configuración WiFi)
v1.1.0  →  v2.0.0  (cambio de protocolo: MQTT v5)

El workflow detecta automáticamente si es un tag de versión (v1.2.0) o un push a main (genera dev-2026-04-16_10-30) y actúa diferente en cada caso.

Paso 2 — Crear el archivo del workflow

Paso 3 — El workflow completo y real

Crea .github/workflows/ota-update.yml con este contenido (es el workflow real del proyecto iot-mqtt-tls):

name: OTA Update to ESP32 via MQTT TLS

on:
  push:
    branches:
      - main          # compila en cada push (sin subir a S3)
    tags:
      - 'v*.*.*'      # compila + sube a S3 + notifica OTA
  pull_request:
    branches:
      - main

jobs:
  build-and-publish:
    runs-on: ubuntu-latest

    steps:
      # 1. Descargar el código fuente
      - name: Checkout repo
        uses: actions/checkout@v3

      # 2. Python es necesario para PlatformIO y los scripts de build
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: 3.11

      # 3. Instalar PlatformIO (el IDE/CLI para ESP32)
      - name: Set up PlatformIO
        run: pip install platformio

      # 4. Detectar si es un tag de versión o un build de desarrollo
      #    - Tag v1.2.0  → FIRMWARE_VERSION=v1.2.0
      #    - Push a main → FIRMWARE_VERSION=dev-2026-04-16_10-30
      - name: Set firmware version
        id: version
        run: |
          if [[ "${GITHUB_REF}" == refs/tags/* ]]; then
            echo "FIRMWARE_VERSION=${GITHUB_REF#refs/tags/}" >> $GITHUB_ENV
          else
            DATE=$(date -u +"%Y-%m-%d_%H-%M")
            echo "FIRMWARE_VERSION=dev-${DATE}" >> $GITHUB_ENV
          fi

      # 5. Definir el nombre del archivo de salida
      - name: Set firmware filename
        run: echo "FIRMWARE_NAME=firmware_${FIRMWARE_VERSION}.bin" >> $GITHUB_ENV

      # 6. Compilar el firmware con PlatformIO
      #    Los secrets se inyectan como variables de entorno que
      #    platformio.ini lee con ${sysenv.VARIABLE}
      - name: Build firmware
        run: platformio run
        env:
          COUNTRY: ${{ secrets.COUNTRY }}
          STATE: ${{ secrets.STATE }}
          CITY: ${{ secrets.CITY }}
          MQTT_SERVER: ${{ secrets.MQTT_SERVER }}
          MQTT_PORT: ${{ secrets.MQTT_PORT }}
          MQTT_USER: ${{ secrets.MQTT_USER }}
          MQTT_PASSWORD: ${{ secrets.MQTT_PASSWORD }}
          WIFI_SSID: ${{ secrets.WIFI_SSID }}
          WIFI_PASSWORD: ${{ secrets.WIFI_PASSWORD }}

      # 7. Subir a S3 (solo cuando es un tag de versión)
      - name: Upload to S3
        if: startsWith(github.ref, 'refs/tags/')
        run: |
          aws s3 cp .pio/build/esp32dev/firmware.bin \
            s3://${{ secrets.S3_BUCKET_NAME }}/$FIRMWARE_NAME \
            --content-type application/octet-stream
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          AWS_DEFAULT_REGION: ${{ secrets.AWS_REGION }}

      # 8. Notificar a los dispositivos por MQTT (solo en tags de versión)
      #    El mensaje JSON indica la versión y la URL de descarga del firmware
      - name: Publish MQTT OTA message
        if: startsWith(github.ref, 'refs/tags/')
        run: |
          pip install paho-mqtt
          python3 -c "
          import os, json, paho.mqtt.publish as publish
          url = 'https://{bucket}.s3.{region}.amazonaws.com/{firmware}'.format(
            bucket=os.getenv('S3_BUCKET_NAME'),
            region=os.getenv('AWS_REGION'),
            firmware=os.getenv('FIRMWARE_NAME')
          )
          payload = json.dumps({
            'version': os.getenv('FIRMWARE_VERSION'),
            'url': url
          })
          publish.single(
            topic=os.getenv('DEVICE_TOPIC'),
            payload=payload,
            hostname=os.getenv('MQTT_SERVER'),
            port=int(os.getenv('MQTT_PORT')),
            auth={'username': os.getenv('MQTT_USER'), 'password': os.getenv('MQTT_PASSWORD')}
                  if os.getenv('MQTT_USER') else None,
            tls={} if os.getenv('MQTT_TLS', 'false') == 'true' else None
          )
          print('OTA message sent:', payload)
          "
        env:
          DEVICE_TOPIC: dispositivo/device1/ota
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          AWS_REGION: ${{ secrets.AWS_REGION }}
          S3_BUCKET_NAME: ${{ secrets.S3_BUCKET_NAME }}
          MQTT_SERVER: ${{ secrets.MQTT_SERVER }}
          MQTT_PORT: ${{ secrets.MQTT_PORT }}
          MQTT_USER: ${{ secrets.MQTT_USER }}
          MQTT_PASSWORD: ${{ secrets.MQTT_PASSWORD }}
          MQTT_TLS: ${{ secrets.MQTT_TLS }}

Desglose del workflow

Cómo PlatformIO recibe los secrets:

platformio.ini define build_flags que leen variables de entorno del sistema:

build_flags =
    -D MQTT_SERVER=\"${sysenv.MQTT_SERVER}\"
    -D MQTT_PORT=${sysenv.MQTT_PORT}
    -D WIFI_SSID=\"${sysenv.WIFI_SSID}\"

Cuando GitHub Actions pone los secrets como variables de entorno en el step de Build firmware, PlatformIO los lee y los inyecta como macros #define en el código C++. El binario compilado ya lleva las credenciales adentro.

El mensaje MQTT que recibe el ESP32:

{
  "version": "v1.2.0",
  "url": "https://firmwares.denkitronik.com.s3.sa-east-1.amazonaws.com/firmware_v1.2.0.bin"
}

El ESP32 (con libota.cpp) está suscrito al tópico dispositivo/device1/ota. Al recibir este JSON, descarga el binario desde la URL y aplica la actualización OTA en un hilo separado sin interrumpir la operación normal.

La condición

if: startsWith(github.ref, 'refs/tags/')

:

Los steps 7 y 8 solo corren cuando el evento es un tag (no en push a main). Esto permite compilar en cada commit para detectar errores, pero solo publicar firmwares oficiales cuando creas explícitamente una versión.

10. Buenas prácticas de seguridad

Un repositorio de firmwares en producción requiere medidas de seguridad adicionales.
1. Rotación de credenciales

Las Access Keys no deben ser permanentes. Establece una política de rotación:

# Crear nueva clave
aws iam create-access-key --user-name github-actions-firmware-uploader

# Actualizar los Secrets en GitHub con la nueva clave
# Luego eliminar la clave anterior
aws iam delete-access-key \
  --user-name github-actions-firmware-uploader \
  --access-key-id AKIAIOSFODNN7EXAMPLE

2. Habilitar MFA Delete en S3

Para prevenir borrados accidentales o maliciosos del bucket:

aws s3api put-bucket-versioning \
  --bucket firmwares.denkitronik.com \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::ACCOUNT-ID:mfa/root-account-mfa-device TOKEN"

3. Notificaciones de publicación

Agrega una notificación por email o Slack cuando se publique un firmware. Agrega este step al workflow:

      - name: Notificar publicación
        if: success()
        run: |
          echo "📦 Nuevo firmware publicado: ${{ steps.version.outputs.VERSION }}"
          # Aquí puedes agregar: curl a Slack webhook, email via SES, etc.

4. Firmar los firmwares

En producción, los firmwares deben llevar una firma digital para verificar su autenticidad:

# Generar firma con GPG
gpg --armor --output firmware.bin.sig --detach-sig firmware.bin

# Subir firma junto al firmware
aws s3 cp firmware.bin.sig \
  s3://firmwares.denkitronik.com/esp32-s3/v1.0.0/firmware.bin.sig

5. Lifecycle policies (gestión del ciclo de vida)

Para controlar costos, configura políticas automáticas. En la consola S3, en Administración → Reglas de ciclo de vida:

Regla
	

Configuración

Mover versiones antiguas a Glacier
	

Versiones no actuales → Glacier después de 90 días

Eliminar versiones muy antiguas
	

Versiones no actuales → Eliminar después de 365 días
6. Auditoría con CloudTrail

Activa AWS CloudTrail para registrar quién descarga qué firmware y cuándo. Esto es obligatorio en contextos regulados (medical devices, automotive, etc.).
