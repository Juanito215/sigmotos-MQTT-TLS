1. Introducción — El sistema que vamos a construir

En el codelab del broker EMQX aprendiste a configurar un servidor MQTT seguro que requiere TLS y autenticación para conectarse. Ahora vamos a construir el otro extremo: el dispositivo físico que se conecta a ese broker, mide el ambiente y publica datos en tiempo real.
El sistema completo

El dispositivo:

    Lee temperatura y humedad cada 2 segundos (sensor SHT21)
    Muestra los datos en una pantalla OLED
    Publica los datos al broker MQTT cifrados con TLS
    Recibe alertas remotas desde el broker y las muestra en pantalla
    Puede recibir una actualización de firmware (OTA) de forma remota
    Si no tiene WiFi configurado, levanta un portal cautivo para que el usuario configure las credenciales

¿Por qué es importante el TLS en IoT?

Imagina un sensor de temperatura en un hospital o en una planta industrial. Sin cifrado, cualquier persona en la misma red puede:

    Leer los datos que publica el dispositivo
    Inyectar mensajes falsos (simular temperaturas normales cuando hay un problema)
    Desconectar el dispositivo enviando comandos maliciosos

TLS (Transport Layer Security) cifra toda la comunicación entre el dispositivo y el broker, igual que HTTPS cifra la comunicación entre tu navegador y un servidor web. En IoT con datos críticos, el TLS no es opcional.

¿Por qué ESP32-S3 y no Arduino UNO? El TLS es computacionalmente costoso. Un Arduino UNO tiene 2KB de RAM y no puede manejar la criptografía de TLS. El ESP32-S3 tiene 512KB de RAM y un coprocesador criptográfico en hardware. Para IoT seguro, necesitas un microcontrolador con más capacidad.

3. Paso 1 — La arquitectura del firmware

Antes de ver una sola línea de código, es fundamental entender cómo está organizado el proyecto y por qué.
¿Qué es el framework Arduino?

Aunque Arduino es conocido como una plataforma de hardware de bajo costo, el framework Arduino es un conjunto de funciones y abstracciones que simplifican la programación de microcontroladores. Al usarlo con ESP32, obtienes:

    Funciones familiares como Serial.println(), delay(), millis()
    Acceso a WiFi, Bluetooth y otras periféricas del ESP32
    Una enorme comunidad de librerías

El punto de entrada de cualquier programa Arduino tiene dos funciones obligatorias:

void setup() {
    // Se ejecuta UNA SOLA VEZ al encender el dispositivo
    // Aquí inicializas hardware, conexiones, etc.
}

void loop() {
    // Se ejecuta en bucle INFINITO después de setup()
    // Aquí va la lógica principal del dispositivo
}

Esto es equivalente a un main() en Java con un while(true) dentro.
¿Qué es PlatformIO?

PlatformIO es el entorno de desarrollo profesional para sistemas embebidos. Es como Maven o Gradle para Java, pero para microcontroladores:

    Gestiona dependencias (librerías externas)
    Compila el código para la arquitectura correcta (ESP32 usa un procesador Xtensa LX7, diferente a x86)
    Sube el firmware al dispositivo
    Abre el monitor serial para ver los mensajes de debug

¿Por qué separar en módulos (lib*.cpp)?

Un firmware monolítico donde todo está en main.cpp puede funcionar para proyectos pequeños, pero se vuelve inmanejable rápidamente. La separación en módulos tiene ventajas concretas:

4. Paso 2 — Configuración segura: el .env y los secrets

Una de las reglas más importantes en desarrollo de software (embebido o no) es: nunca pongas credenciales en el código fuente.
¿Por qué es tan importante?

Si escribes algo como esto en tu código:

// NUNCA HAGAS ESTO
const char* mqtt_server = "mi-broker.com";
const char* mqtt_password = "miPasswordSuperSecreto123";
const char* wifi_password = "ClaveWiFiDeCasa";

Y subes el código a GitHub (incluso en un repositorio privado), esas credenciales quedan expuestas. GitHub tiene bots que escanean repositorios buscando exactamente este tipo de información. En minutos alguien puede robar tus credenciales.
La solución: variables de entorno inyectadas en tiempo de compilación

El proyecto usa un archivo .env (que nunca se sube a git, está en el .gitignore) con todas las credenciales:

# .env.template — copia esto como .env y completa los valores

COUNTRY=colombia
STATE=valle
CITY=tulua
MQTT_SERVER=mqtt.tudominio.freeddns.org
MQTT_PORT=8883
MQTT_USER=alvaro
MQTT_PASSWORD=miPasswordMQTT
WIFI_SSID=MiRedWiFi
WIFI_PASSWORD=MiClaveWiFi
ROOT_CA=-----BEGIN CERTIFICATE-----\nMIIF...\n-----END CERTIFICATE-----

Cuando compilas el firmware, el script build_with_env.py lee este archivo y pasa cada variable como una constante de compilación (-D NOMBRE=valor). El platformio.ini lo configura así:

[env:esp32-s3-devkitc-1]
platform = espressif32
board = esp32-s3-devkitc-1
framework = arduino

build_flags =
    -D COUNTRY=\"${sysenv.COUNTRY}\"
    -D STATE=\"${sysenv.STATE}\"
    -D CITY=\"${sysenv.CITY}\"
    -D MQTT_SERVER=\"${sysenv.MQTT_SERVER}\"
    -D MQTT_PORT=${sysenv.MQTT_PORT}
    -D MQTT_USER=\"${sysenv.MQTT_USER}\"
    -D MQTT_PASSWORD=\"${sysenv.MQTT_PASSWORD}\"
    -D WIFI_SSID=\"${sysenv.WIFI_SSID}\"
    -D WIFI_PASSWORD=\"${sysenv.WIFI_PASSWORD}\"

El ${sysenv.VARIABLE} le dice a PlatformIO que lea esa variable del entorno del sistema. El script Python se encarga de cargar el .env al entorno antes de compilar.
¿Qué hace secrets.cpp?

secrets.cpp declara las variables que el resto del código usará, tomando los valores de las constantes de compilación:

// secrets.cpp — recibe los valores del .env en tiempo de compilación

const char* mqtt_server   = MQTT_SERVER;     // viene del .env
const int   mqtt_port     = MQTT_PORT;       // 8883
const char* mqtt_user     = MQTT_USER;       // tu usuario MQTT
const char* mqtt_password = MQTT_PASSWORD;   // tu password MQTT

// Certificado raíz TLS (Let's Encrypt ISRG Root X1 por defecto)
const char* root_ca =
"-----BEGIN CERTIFICATE-----\n"
"MIIFazCCA1OgAwIBAgIRAIIQz7DSQONZRGPgu2OCiwAwDQYJKoZIhvcNAQELBQAw\n"
// ... (resto del certificado)
"-----END CERTIFICATE-----\n";

Los tópicos MQTT — cómo se construyen

Una decisión de diseño muy inteligente del proyecto es construir los tópicos MQTT usando la ubicación geográfica del dispositivo + su dirección MAC:

// Estructura del tópico:
// <PAÍS>/<ESTADO>/<CIUDAD>/<MAC_DISPOSITIVO>/<USUARIO_MQTT>/out
// <PAÍS>/<ESTADO>/<CIUDAD>/<MAC_DISPOSITIVO>/<USUARIO_MQTT>/in

// Ejemplo con los valores del .env:
// colombia/valle/tulua/ESP32-A1B2C3D4E5F6/alvaro/out  ← publica datos
// colombia/valle/tulua/ESP32-A1B2C3D4E5F6/alvaro/in   ← recibe comandos

¿Por qué incluir la ubicación y la MAC? Porque en un sistema IoT real con decenas o cientos de dispositivos, necesitas identificar cada uno de forma única. La MAC garantiza unicidad (cada ESP32 tiene una MAC diferente de fábrica). La ubicación permite filtrar por región en el broker.

colombia/             ← filtra por país
  valle/              ← filtra por departamento
    tulua/            ← filtra por ciudad
      ESP32-A1B2.../  ← identifica el dispositivo exacto
        alvaro/       ← identifica al usuario/tenant
          out         ← datos que el dispositivo publica
          in          ← comandos que el dispositivo recibe

Un suscriptor interesado en todos los dispositivos de Tuluá usaría el comodín MQTT: colombia/valle/tulua/#

5. Paso 3 — TLS en un dispositivo embebido

TLS es el protocolo que garantiza que la comunicación entre el ESP32 y el broker es:

    Cifrada: nadie puede leer los mensajes en tránsito
    Auténtica: el ESP32 verifica que está hablando con el broker real y no con un impostor

¿Cómo funciona TLS? (versión simplificada)

La clave del proceso es el certificado raíz (Root CA). Es la firma de una entidad de confianza (Let's Encrypt, en nuestro caso) que certifica que el certificado del broker es legítimo. El ESP32 verifica esta firma antes de confiar en cualquier datos que llegue.
La cadena de confianza

![[tls_chain.png]]

Si alguien intentara hacer un ataque "man in the middle" (interceptar la comunicación fingiendo ser el broker), el ESP32 rechazaría la conexión porque el atacante no puede obtener un certificado firmado por Let's Encrypt para un dominio que no controla.
La implementación en código

En libiot.cpp, la función reconnect() establece la conexión TLS + MQTT:

void reconnect() {
    while (!client.connected()) {

        // PASO 1: Configurar el certificado raíz
        // Esto le dice al ESP32 qué autoridad certificadora confiar
        espClient.setCACert(root_ca);

        // PASO 2: Intentar la conexión MQTT
        // El cliente_id identifica a este dispositivo en el broker
        String client_id = getMacAddress();  // "ESP32-A1B2C3D4E5F6"

        if (client.connect(client_id.c_str(), mqtt_user, mqtt_password)) {
            // PASO 3: Conexión exitosa — suscribirse al tópico de entrada
            client.subscribe(MQTT_TOPIC_SUB, 1);  // QoS 1

            Serial.println("Conectado al broker MQTT con TLS ✓");
        } else {
            // PASO 4: Conexión fallida
            int state = client.state();

            if (state == -4) {
                Serial.println("Timeout — broker no responde");
            } else if (state == 5) {
                // Credenciales incorrectas — dormir 5 minutos
                // para no saturar el broker con intentos fallidos
                Serial.println("Credenciales inválidas — deep sleep");
                esp_deep_sleep(300 * 1000000ULL);  // 5 minutos en microsegundos
            }

            delay(5000);  // esperar 5 segundos antes de reintentar
        }
    }
}

¿Por qué

esp_deep_sleep

en caso de error de autenticación?

Si las credenciales están mal, cada intento de reconexión consume:

    Energía de la batería (en dispositivos IoT alimentados por batería esto importa mucho)
    Recursos del broker (que podría bloquearte por demasiados intentos fallidos)

El deep sleep pone el ESP32 en un estado de consumo ultra bajo (~10 µA vs. ~240 mA en operación normal) durante 5 minutos. Es como poner el dispositivo en "modo hibernación".
¿Qué es QoS en MQTT?

Al suscribirse, el código usa client.subscribe(MQTT_TOPIC_SUB, 1). El 1 es el nivel de Quality of Service (QoS):

QoS
	

Garantía
	

Cuándo usarlo

0
	

El mensaje se envía una vez. Puede perderse.
	

Datos frecuentes donde una pérdida es aceptable (temperatura cada 2 seg)

1
	

El mensaje llega al menos una vez. Puede duplicarse.
	

Alertas, comandos importantes

2
	

El mensaje llega exactamente una vez.
	

Transacciones críticas, comandos de control

El proyecto usa QoS 1 para la suscripción (alertas y OTA): es preferible recibir una alerta duplicada a no recibirla. Y QoS 0 implícito para publicar datos del sensor: si se pierde una lectura de temperatura, la siguiente llega 2 segundos después.
¿Por qué el puerto 8883?

MQTT estándar usa el puerto 1883 (sin cifrado). MQTT sobre TLS usa el puerto 8883, igual que HTTPS usa el 443 en lugar del HTTP 80. Es una convención que permite a firewalls y routers tratar el tráfico MQTT seguro diferente al inseguro.


6. Paso 4 — WiFi: conexión y provisioning
El problema del primer arranque

Cuando fabricas un dispositivo IoT, no sabes en qué red WiFi lo va a usar el cliente final. No puedes hardcodear el SSID y password en el firmware porque cada cliente tiene una red diferente.

La solución es el provisioning: la primera vez que el dispositivo arranca sin credenciales WiFi, se convierte temporalmente en un punto de acceso WiFi y levanta una página web donde el usuario ingresa sus credenciales.
¿Dónde guarda las credenciales? NVS

NVS (Non-Volatile Storage) es una partición especial de la memoria flash del ESP32 diseñada para guardar pares clave-valor de forma persistente. Es como un SharedPreferences de Android o el registro de Windows, pero para microcontroladores.

¿Por qué NVS y no simplemente escribir en la memoria flash directamente?

    La flash normal tiene un límite de escrituras (~100,000 ciclos). NVS implementa wear leveling: distribuye las escrituras en toda la partición para que no se desgaste siempre el mismo sector
    NVS maneja la corrupción: si el dispositivo se apaga mientras escribe, los datos antiguos siguen intactos
    Interfaz sencilla: simplemente lees y escribes por nombre de clave

// libstorage.cpp — guardar credenciales WiFi

void saveWiFiCredentials(const String& ssid, const String& password) {
    Preferences prefs;
    prefs.begin("cred", false);     // abre namespace "cred" en modo lectura/escritura
    prefs.putString("wifi_ssid", ssid);
    prefs.putString("wifi_pwd", password);
    prefs.end();                    // cierra y confirma la escritura
}

bool loadWiFiCredentials(String& outSsid, String& outPassword) {
    Preferences prefs;
    prefs.begin("cred", true);      // abre en modo solo lectura
    outSsid = prefs.getString("wifi_ssid", "");
    outPassword = prefs.getString("wifi_pwd", "");
    prefs.end();
    return (outSsid.length() > 0);  // retorna true si encontró credenciales
}

El flujo de provisioning paso a paso

// libprovision.cpp — crear el AP y el servidor web

void startProvisioningAP() {
    // Crear un nombre de AP único usando los últimos bytes de la MAC
    String apName = "ESP32-Setup-" + getHostname().substring(12, 18);

    // Iniciar en modo AP (Access Point)
    WiFi.softAP(apName.c_str());
    WiFi.softAPConfig(
        IPAddress(192, 168, 4, 1),   // IP del AP
        IPAddress(192, 168, 4, 1),   // Gateway
        IPAddress(255, 255, 255, 0)  // Máscara de subred
    );

    // Registrar los handlers HTTP
    server.on("/", HTTP_GET, handleRoot);    // muestra el formulario
    server.on("/save", HTTP_POST, handleSave); // procesa el formulario

    server.begin();
    Serial.println("Portal de provisioning activo en 192.168.4.1");
}

void handleSave() {
    String ssid = server.arg("ssid");
    String password = server.arg("password");

    // Guardar en NVS
    saveWiFiCredentials(ssid, password);

    // Responder al navegador
    server.send(200, "text/html",
        "<h3>¡Guardado! El dispositivo se reiniciará.</h3>");

    delay(2000);
    ESP.restart();  // reiniciar el ESP32
}

Factory Reset: borrón y cuenta nueva

Si el usuario cambia de red WiFi o quiere resetear el dispositivo, el firmware detecta si el botón BOOT (GPIO0) se mantiene presionado durante 3 segundos en el arranque:

// En setup() — detección de factory reset

void checkFactoryReset() {
    pinMode(0, INPUT_PULLUP);  // GPIO0 = botón BOOT

    unsigned long pressStart = millis();

    // Si el botón está presionado al encender...
    while (digitalRead(0) == LOW) {
        if (millis() - pressStart >= 3000) {
            // 3 segundos presionado = factory reset
            Serial.println("Factory Reset iniciado...");
            clearWiFiCredentials();  // borra de NVS
            WiFi.disconnect(true);   // desconecta y borra credenciales de WiFi
            ESP.restart();           // reinicia — arrancará en modo provisioning
        }
    }
}

¿Por qué 3 segundos y no inmediato? Para evitar factory resets accidentales. Si el botón se usa para otras cosas (diagnóstico, por ejemplo), una pulsación corta no debe resetear el dispositivo.


7. Paso 5 — El núcleo IoT: sensores, publicación y callbacks
Inicialización del sistema IoT

La función setupIoT() en libiot.cpp configura todo lo relacionado con MQTT y el sensor:

void setupIoT() {
    // 1. Inicializar el bus I2C para el sensor SHT21 y la pantalla OLED
    //    SDA = GPIO8, SCL = GPIO9 (pines I2C del ESP32-S3)
    Wire.begin(8, 9);

    // 2. Configurar el certificado TLS
    espClient.setCACert(root_ca);

    // 3. Configurar el cliente MQTT
    client.setServer(mqtt_server, mqtt_port);  // 8883 con TLS

    // 4. Aumentar el buffer de mensajes MQTT
    //    Por defecto el buffer es 256 bytes — muy pequeño para JSON con el certificado
    client.setBufferSize(1024);

    // 5. Registrar el callback para mensajes entrantes
    client.setCallback(receivedCallback);

    // 6. Sincronizar la hora con servidores NTP
    setTime();

    // 7. Inicializar el sensor SHT21
    setupSHT();
}

¿Por qué sincronizar la hora?

TLS requiere verificar la vigencia del certificado: cada certificado tiene una fecha de inicio y una fecha de expiración. Si el ESP32 no sabe la hora actual, no puede verificar si el certificado es válido. Un ESP32 recién encendido cree que es el 1 de enero de 1970 (epoch time). Hay que sincronizarlo antes de intentar la conexión TLS.

void setTime() {
    // NTP: Network Time Protocol — protocolo para sincronizar relojes en red
    configTime(
        -5 * 3600,      // UTC-5 (hora Colombia)
        0,              // sin horario de verano
        "pool.ntp.org", // servidor NTP primario
        "time.nist.gov" // servidor NTP secundario (backup)
    );

    Serial.print("Sincronizando hora con NTP");

    // Esperar hasta que la hora sea válida (> año 2024)
    time_t now = time(nullptr);
    while (now < 1700000000) {
        delay(500);
        Serial.print(".");
        now = time(nullptr);
    }

    Serial.println(" OK");
    Serial.printf("Hora actual: %s", ctime(&now));
}

Leyendo el sensor SHT21

El SHT21 se comunica por I2C (Inter-Integrated Circuit), un protocolo de comunicación serial que usa solo 2 cables:

    SDA (Serial Data): transmite los datos
    SCL (Serial Clock): sincroniza la transmisión

La librería arduino-sht abstrae completamente el protocolo. Solo debes llamar a las funciones de lectura:

void setupSHT() {
    // Inicializar el sensor con precisión media
    // (balance entre velocidad de medición y precisión)
    sht.setAccuracy(SHTSensor::SHT_ACCURACY_MEDIUM);
}

bool measure(SensorData* data) {
    // MEASURE_INTERVAL = 2000 ms (2 segundos)
    // No tiene sentido medir más rápido que eso para temperatura/humedad
    if (millis() - lastMeasureTime < MEASURE_INTERVAL) {
        return false;  // todavía no es tiempo de medir
    }

    lastMeasureTime = millis();

    if (sht.readSample()) {
        data->temperature = sht.getTemperature();
        data->humidity    = sht.getHumidity();
        return true;
    }

    return false;  // error de lectura del sensor
}

Publicando datos al broker MQTT

void sendSensorData(float temp, float humidity) {
    // Construir el mensaje JSON
    // Usamos ArduinoJson para construir el JSON de forma segura
    StaticJsonDocument<128> doc;
    doc["temperatura"] = temp;
    doc["humedad"]     = humidity;

    char buffer[128];
    serializeJson(doc, buffer);
    // buffer ahora contiene: {"temperatura":25.5,"humedad":60.2}

    // Publicar al broker MQTT
    // MQTT_TOPIC_PUB = "colombia/valle/tulua/ESP32-A1B2.../alvaro/out"
    bool success = client.publish(MQTT_TOPIC_PUB, buffer);

    if (success) {
        Serial.printf("Publicado: %s → %s\n", MQTT_TOPIC_PUB, buffer);
    } else {
        Serial.println("Error al publicar — reconectando...");
    }
}

¿Por qué JSON? El JSON es el formato estándar para intercambio de datos en IoT porque:

    Es legible por humanos (útil para debug)
    Todos los lenguajes y plataformas pueden parsearlo
    El broker puede enrutar mensajes filtrando por campos del JSON
    Un dashboard como Grafana puede extraer temperatura y humedad directamente

El callback: procesando mensajes entrantes

En MQTT el modelo es asíncrono: el broker puede enviarle un mensaje al ESP32 en cualquier momento. El ESP32 registra una función callback que se ejecuta automáticamente cada vez que llega un mensaje al tópico suscrito.

// Este callback se registró en setupIoT():
// client.setCallback(receivedCallback);

void receivedCallback(char* topic, byte* payload, unsigned int length) {
    // Convertir el payload (bytes) a String para facilitar el procesamiento
    String message = "";
    for (unsigned int i = 0; i < length; i++) {
        message += (char)payload[i];
    }

    Serial.printf("Mensaje recibido en [%s]: %s\n", topic, message.c_str());

    // CASO 1: ¿Es un mensaje de actualización OTA?
    // El tópico OTA es diferente al tópico normal de entrada
    if (String(topic) == OTA_TOPIC) {
        checkOTAUpdate(message.c_str());
        return;
    }

    // CASO 2: ¿Contiene la palabra "ALERT"?
    if (message.indexOf("ALERT") >= 0) {
        // Mostrar la alerta en la pantalla OLED durante 60 segundos
        currentAlert = message;
        alertStartTime = millis();
        Serial.println("¡Alerta recibida!");
    }
}

¿Cómo funciona

client.loop()

?

En el loop() principal del firmware hay una llamada a client.loop(). Esta función:

    Lee el buffer de red (verifica si llegó algún mensaje del broker)
    Si llegó un mensaje, llama al callback receivedCallback
    Envía pings de keepalive al broker (para que el broker sepa que el dispositivo sigue activo)
    Mantiene la conexión TCP viva

Sin client.loop(), el callback nunca se ejecutaría y el broker pensaría que el dispositivo está desconectado.

8. Paso 6 — La pantalla OLED y el display loop

La pantalla OLED de 128x64 píxeles usa el controlador SSD1306 y se comunica por I2C (los mismos pines que el sensor SHT21 — I2C permite múltiples dispositivos en el mismo bus).
¿Qué muestra la pantalla?

La pantalla se actualiza en cada iteración del loop() y muestra:

Pantalla OLED

Cuando llega una alerta, el estado "OK" es reemplazado por el mensaje de alerta durante 60 segundos.
La función displayLoop

void displayLoop(String message, time_t now, float temp, float humi) {
    display.clearDisplay();  // borrar todo lo que había antes

    displayHeader(now);              // línea 1: "IOT Sensors HH:MM:SS"
    displayMeasures(temp, humi);     // línea 2: "T: 24.3    H: 65.1"
    displayMessage(message);         // línea 3: "OK" o mensaje de alerta

    display.display();  // enviar el buffer a la pantalla (sin esto no se ve nada)
}

¿Por qué

clearDisplay()

en cada frame? La librería del OLED trabaja con un buffer en memoria RAM del ESP32. Cuando llamas a display.clearDisplay(), limpias ese buffer. Luego dibujas lo nuevo y display.display() envía todo el buffer por I2C a la pantalla. Sin el clear, los píxeles del frame anterior quedarían superpuestos.

. Paso 7 — Actualizaciones OTA (Over-The-Air)

OTA permite actualizar el firmware del dispositivo remotamente sin necesidad de conectar un cable USB. Es esencial en IoT real: si tienes 100 dispositivos desplegados en campo, no puedes ir a cada uno a actualizar el firmware manualmente.
El flujo OTA completo

El código OTA en el ESP32

// libota.cpp

void checkOTAUpdate(const char* payload) {
    // El payload es JSON: {"version":"v1.2.0","url":"https://..."}
    StaticJsonDocument<512> doc;
    deserializeJson(doc, payload);

    const char* version = doc["version"];
    const char* url     = doc["url"];

    if (!url || !version) {
        Serial.println("Payload OTA inválido");
        return;
    }

    String currentVersion = getFirmwareVersion();

    if (String(version) == currentVersion) {
        Serial.println("Ya tengo esta versión — OTA ignorado");
        return;
    }

    Serial.printf("Nueva versión disponible: %s → %s\n",
                  currentVersion.c_str(), version);

    // Iniciar la descarga en una tarea FreeRTOS separada
    // para no bloquear el loop principal
    startOTATask(url, version);
}

void performOTAUpdate(const char* url, const char* version) {
    Serial.printf("Descargando firmware desde: %s\n", url);

    // HTTPUpdate es una librería del ESP32 que descarga
    // y flashea el firmware en un solo paso
    WiFiClientSecure client;
    client.setInsecure();  // en producción usa certificado del servidor S3

    t_httpUpdate_return result = httpUpdate.update(client, url);

    switch (result) {
        case HTTP_UPDATE_OK:
            // El dispositivo se reinicia automáticamente
            saveFirmwareVersion(version);
            Serial.println("OTA exitoso — reiniciando...");
            break;
        case HTTP_UPDATE_FAILED:
            Serial.printf("OTA fallido: %s\n",
                          httpUpdate.getLastErrorString().c_str());
            break;
    }
}

¿Por qué usar una tarea FreeRTOS separada para el OTA?

La descarga del firmware puede tardar 30-60 segundos. Si bloqueas el loop() principal durante ese tiempo:

    El cliente MQTT pierde la conexión (el broker no recibe keepalives)
    La pantalla OLED se congela
    Si hay un error de red a mitad de la descarga, el loop nunca se recupera

Ejecutar el OTA en una tarea FreeRTOS separada permite que el loop principal siga funcionando durante la descarga.

void startOTATask(const char* url, const char* version) {
    // FreeRTOS permite correr código en paralelo en los 2 núcleos del ESP32-S3
    xTaskCreatePinnedToCore(
        performOTAUpdateTask,  // función que ejecuta la tarea
        "OTA_Task",            // nombre de la tarea (para debug)
        8192,                  // tamaño del stack en bytes
        params,                // parámetros (url y version)
        1,                     // prioridad (1 = baja, el loop principal tiene más)
        NULL,                  // handle de la tarea (no lo necesitamos)
        1                      // ejecutar en el núcleo 1
                               // (núcleo 0 = loop principal)
    );
}

Ahora que entiendes cada módulo, veamos cómo main.cpp los orquesta:
La función setup()

void setup() {
    Serial.begin(115200);
    Serial.println("\n\n=== Iniciando firmware IoT v" + getFirmwareVersion() + " ===");

    // PASO 1: Verificar factory reset antes de cualquier otra cosa
    checkFactoryReset();

    // PASO 2: Escanear redes WiFi disponibles (útil para debug)
    listWiFiNetworks();

    // PASO 3: Inicializar la pantalla OLED
    // (necesitamos mostrar estado durante el resto del setup)
    startDisplay();

    // PASO 4: Verificar si hay credenciales WiFi guardadas
    if (!hasStoredWiFi()) {
        // Sin credenciales → modo provisioning
        Serial.println("Sin WiFi configurado → iniciando provisioning");
        startProvisioningAP();

        // El loop() manejará el portal cautivo hasta que el usuario
        // ingrese las credenciales y el dispositivo se reinicie
        return;
    }

    // PASO 5: Conectar al WiFi con las credenciales guardadas
    display.clearDisplay();
    displayConnecting(getHostname());
    startWiFi(getHostname().c_str());

    // PASO 6: Inicializar MQTT, sensor y sincronizar hora
    setupIoT();

    Serial.println("=== Setup completado ===");
}

La función loop()

void loop() {
    // CASO ESPECIAL: si estamos en modo provisioning,
    // solo manejamos el portal cautivo
    if (isProvisioning()) {
        provisioningLoop();
        return;
    }

    // VERIFICACIÓN 1: ¿WiFi conectado?
    checkWiFi();  // intenta reconectar si es necesario

    // VERIFICACIÓN 2: ¿MQTT conectado?
    checkMQTT();  // llama a reconnect() si es necesario
                  // y ejecuta client.loop() para procesar mensajes

    // MEDICIÓN: ¿Ya pasaron 2 segundos desde la última medición?
    SensorData data;
    if (measure(&data)) {
        // PUBLICACIÓN: enviar datos al broker
        sendSensorData(data.temperature, data.humidity);
    }

    // DISPLAY: actualizar la pantalla OLED
    time_t now = time(nullptr);
    String alertMsg = checkAlert();  // retorna "OK" o el mensaje de alerta activo
    displayLoop(alertMsg, now, data.temperature, data.humidity);
}

El patrón de reconexión en checkMQTT()

void checkMQTT() {
    if (!client.connected()) {
        reconnect();  // intenta reconectar con TLS
    }

    client.loop();  // SIEMPRE llamar, incluso si acaba de reconectar

    // Health check cada 30 segundos
    if (millis() - lastHealthCheck > 30000) {
        lastHealthCheck = millis();
        Serial.printf("[Health] WiFi RSSI: %d dBm | MQTT: %s | "
                      "Temp: %.1f°C | Hum: %.1f%%\n",
                      WiFi.RSSI(),
                      client.connected() ? "OK" : "DESCONECTADO",
                      lastTemp, lastHumidity);
    }
}

¿Qué es el RSSI? Es la potencia de la señal WiFi recibida, medida en dBm (decibel-miliwatts):

    -30 dBm: señal excelente (estás al lado del router)
    -70 dBm: señal aceptable
    -90 dBm: señal muy débil, conexiones inestables

El health check lo imprime cada 30 segundos para ayudar en el diagnóstico de problemas de campo.
